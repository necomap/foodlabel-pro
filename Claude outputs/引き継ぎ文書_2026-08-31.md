## この環境（Cowork/Claude）特有の制約・作業パターン

**重要: このセッションでは `device_bash`（ユーザーPC上のシェル）が使えない。** 使えるのは以下のみ:
- `mcp__remote-devices__device_list_dir`
- `mcp__remote-devices__device_stage_files`（PC→クラウドへダウンロード）
- `mcp__remote-devices__device_commit_files`（クラウド→PCへ書き込み）
- `mcp__remote-devices__get_device_info`

そのため、コード修正は毎回このパターンで行う:
1. `device_stage_files` で対象ファイルを `/mnt/user-data/uploads/foodlabel-pro/...` にステージング
2. `Read`/`Edit` でクラウド側のローカルコピーを編集
3. 単体の `tsc --noEmit` で構文チェック（下記「tscチェックの手順」参照）
4. `SendUserFile` で確定内容を配信（`file_uuid` を控える）
5. `device_commit_files` で `file_uuid` を使ってPCへ書き戻す

### ⚠️ 致命的な落とし穴（今回の教訓）
`device_stage_files` は **PC上の現在の内容でローカルコピーを上書きする**。編集済みのファイルに対して「mtimeだけ新しく取得したい」といった理由で再度 `device_stage_files` を呼ぶと、編集内容がPC側の古い内容で **上書き（破壊）される**。
ただし `SendUserFile` は呼び出し時点の内容を `file_uuid` として独立にスナップショットするため、後から同じパスを再ステージして壊しても、`file_uuid` を使った `device_commit_files` は影響を受けない（今回はこれで実害なく回避できたが、必ず確認作業を挟むこと）。
**教訓: 一度編集してSendUserFileした後は、同じパスに `device_stage_files` を再度かけない。** mtimeガードが必要な場合は、編集前の最初のステージ時点のmtimeを使うか、コミット後に別途ステージし直して内容を検証する。

### tscチェックの手順
プロジェクト内で `npx tsc` を実行すると `TS5112`（tsconfig.jsonとコマンドライン--targetの競合）で失敗する。回避策:
- `/tmp` など tsconfig.json が存在しないディレクトリに移動してから、グローバルの `tsc` バイナリ（`/home/claude/.npm-global/bin/tsc`）を直接呼ぶ
- 例: `cd /tmp && tsc --noEmit --jsx react --esModuleInterop --skipLibCheck --target es2020 /mnt/user-data/uploads/foodlabel-pro/app/api/xxx/route.ts`
- 以下のエラーは **既知の誤検知**（node_modules/Prisma生成型が無い環境ゆえ）なので無視してよい: `Cannot find module`, `JSX.IntrinsicElements`, `React' to be in scope`, `implicitly has an 'any' type`, `Cannot find name 'process'/'Buffer'`, `.map()` の `key` prop型エラー, `Property 'X' does not exist on type '{}'`（Prismaの戻り値型が解決できないことによる連鎖エラー）

### tsconfig.json の target 制約
プロジェクトの `tsconfig.json` に明示的な `target` が無く、TypeScript 5.5.3 環境ではES2015未満扱いになる。そのため **`Map` を `for...of` でイテレートするとビルドエラー**になる（配列は問題ない）。`Map.forEach((value, key) => {...})` を使うこと。
