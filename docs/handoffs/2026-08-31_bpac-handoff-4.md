## 3. 【未解決・仕様確認が必要】非表示にしたレシピを再インポートすると新規作成される

**ユーザーからの質問**：「インポート→未使用のレシピを非表示→再度インポート、とした場合、未使用レシピの分は新しく作成されてしまう？」

**コードを確認した結果、その通りになることを確認済み（未修正）**。

原因：`app/api/import-export/route.ts`の重複チェック・上書き処理が、どちらも`isActive: true`のレシピのみを対象にしている。

```ts
const existingRecipes = await prisma.recipe.findMany({
  where: { userId: session.user.id, isActive: true },   // ← 非表示(isActive:false)は含まれない
  select: { id: true, name: true },
});
```

- 上書きOFFの場合：同名チェック（`recipeCache.get(name)`）で非表示レシピはヒットしないため、スキップされず新規作成される。
- 上書きONの場合：既存を論理削除する`updateMany`も`isActive: true`だけを対象にしているため、非表示レシピは対象にならず素通りし、結局新規作成される。

結果として、非表示レシピはDBに残り続け（今の仕様では「非表示」と「論理削除」が同じ`isActive`フィールドを共有している）、同名の新しいレシピが別レコードとして積み重なっていく。

**このチャットでは未修正**（バグとも仕様とも取れるため、対応するかどうかユーザーへの確認が必要と判断し保留にした）。対応する場合の選択肢の例：

1. 重複チェックを`isActive`を問わず名前一致で見るようにし、非表示レシピも「上書き対象」（＝再インポートで復活）として扱う。
2. 非表示レシピを画面から一括削除できる機能を別途用意し、定期的に整理してもらう運用にする。
3. 現状維持（非表示＝そのユーザーにとって「もう要らないもの」という前提なら、新規作成される方が自然という考え方もある）。

次のチャットでユーザーに意向を確認してから対応すること。

## 5. b-PACラベルのキャプション重複バグ修正＋表示切替機能の実装→撤去

### 5.1 バグ修正（維持）

- `lib/bpac-print.ts`の`buildTextFields()`：`nutritionLabel`が`content.nutritionPerUnit.label`（例：「1個あたり」）をそのまま差し込んでいたが、テンプレート側のキャプションに既に「あたり」が含まれており「1個あたりあたり」の二重表示になっていた。末尾の「あたり」を`.replace(/あたり$/, '')`で除去し、「1個」のみ差し込むように修正。
- `lib/label.ts`の`buildManufacturerBlockText()`（b-PAC専用の文字列生成関数。ブラウザ印刷用の同名関数とは別物なので注意）：「製造者：」というプレフィックスをコード側で付けていたが、これもテンプレート側キャプションと二重表示になっていたため削除。

### 5.2 表示切替機能（実装したが撤去済み）

当初、「あたり」「製造者：」「商品名：」を`captionUnit`・`captionManufacturer`・`captionProductName`という別オブジェクトとしてテンプレートに用意してもらい、チェックボックスで表示・非表示を切り替える機能（`OPTIONAL_CAPTION_TEXTS`、`printFoodLabel()`の第3引数`showCaptions`、`labels/page.tsx`の`bpacShowCaptions`state）を実装した。

しかしユーザーからの後日談で、想定していたのは「あたり・製造者・商品名の3つだけでなく、他の全項目のキャプション」であり、かつ「テンプレートにキャプション専用オブジェクトを追加する運用は結局手間で、そのままダイレクトに表示した方が分かりやすい」との結論になったため、**この切り替え機能は全て撤去した**（`lib/bpac-print.ts`・`app/dashboard/labels/page.tsx`とも元の状態＝5.1のバグ修正のみが残る状態に戻した）。

今後もし項目名の表示切替が話題に上がった場合は、「コード側で動的に出し分けるのではなく、テンプレート側で必要な項目だけキャプション込みの静的テキストとして直接作る」のが本人の結論であることを踏まえること。「商品名：」はユーザーの現テンプレートでは使っておらず、代わりに品名（`productName`オブジェクト）を直接使っている。

## 6. Excelインポートの80件上限を1ボタンで自動処理できるように改善

**経緯**：1リクエストあたり最大80件（Vercelのタイムアウト対策）という制限があり、ユーザーはこれまでExcelマクロで手動でファイルを分割してから1つずつインポートしていた。「アプリ側で自動的に分割処理してほしい、理想はワンボタン」という要望に対応。

**実装内容**：

- `app/api/import-export/route.ts`のPOSTに`offset`パラメータを追加。1回のリクエストでは`offset`から最大80件だけ処理し、`done`（全件処理完了 or プラン上限到達で打ち切り）と`nextOffset`をレスポンスで返す。
- 全削除（`clearAll`）・月間インポート回数カウント（`logDataTransfer`）は、一連の操作の最初のリクエスト（`offset === 0`）でのみ実行するようガード（2回目以降のチャンクで誤って多重実行されないように）。
- `parseExcelFile()`が返すファイルレベルのエラー・警告（行の値が読めない等）は、再パースするたびに毎回同じ内容が返ってくるため、最初のチャンクのレスポンスにのみ含めるようにして重複を防止。
- `app/dashboard/import/page.tsx`側は、`done`になるまで自動的に`offset`を進めながら繰り返しリクエストするループを実装。ユーザー操作はファイル選択＋ボタン1回のみで完結する。進捗表示（「取り込み中... (240/700件)」）とプログレスバーを追加。処理中にタブを閉じないよう`beforeunload`で警告。
- **副次的に発見・修正したバグ**：旧実装では80件を超えるファイルを分割せず1回で送ると、81件目以降が**警告も無いまま無言でインポートされない**状態だった（`total`には全件数が表示されるのに、実際に処理されるのは80件のみ）。現在はプラン上限（レシピ件数上限）で打ち切られた場合のみ、明示的な警告メッセージを返すように修正。
- 処理速度自体は変わらない（1件あたり約3秒の実績のまま）ため、件数が多い場合（例：700件で約35分）は依然として時間がかかる。ユーザーには「タブを閉じずに待ってほしい」旨を案内済み。処理が途中で止まっても、同じファイルを再度インポートし直せば（上書きOFFなら重複分は自動スキップされるため）続きから進められる、という設計。

## 8. 非表示レシピの再インポート問題 → 修正（本セクションが最重要・要db push）

### 8.1 何が起きていたか（実際にユーザーが踏んだ不具合）

「既存レシピ削除して取り込み」（＝インポート画面の「全データをクリアして上書き」チェック）を使ったところ、
「110件取り込み成功」の後「行111: プレミアムプランのレシピ上限（100件）に達したため、残り427件は取り込まれませんでした」と表示され、
実際に確認すると登録（表示）レシピ98件・非表示レシピ167件という辻褄の合わない結果になった。

**根本原因（このセクション以前のバグ。すでに修正済み＝下記8.2参照）**：

1. 「全データをクリアして上書き」は、名前に反して実際には物理削除ではなく**非表示化**（`isActive = false`に更新するだけ）だった。
2. インポート時の「同名レシピか判定」ロジックが**表示中（isActive:true）のレシピしか見ていなかった**。
3. そのため①で全レシピが非表示化された直後は「同名レシピ」が1件も見つからず、インポートした行が**すべて新規（表示）レシピとして作成**される。
4. これが表示レシピの上限（プレミアムは100件）に達するまで続き、達した時点で残りの行が打ち切られる。
5. 結果、旧レシピ（今回の167件の非表示レシピの中身）はそのまま非表示のゴミとして残り続け、新規に作られた分だけが表示レシピとしてカウントされる、という状態になっていた。

これは6章で対応した「インポート→未使用レシピを非表示→再度インポートすると重複作成される」問題と**同じ根本原因**（非表示レシピが同名判定から漏れている）。

### 8.2 このセッションで実施した修正内容

- `app/api/import-export/route.ts`：同名レシピ検索を「表示・非表示問わず全レシピ」に変更。上書き時は`id`指定で対象を特定するように変更。
- 新しいレシピの表示/非表示状態は次の優先順位で決定：①Excelの新設「FLG」列に明示的な「表示」「非表示」指定があればそれに従う → ②指定が無く既存の同名レシピ（非表示含む）を上書きする場合はその非表示状態を引き継ぐ（季節限定レシピ等が勝手に表示に戻らないように）→ ③どちらでもない新規レシピは表示状態で作成。
- `lib/excel-import-export.ts`：エクスポートファイルの「FLG」列（元々常に空欄だった予約列。列位置はズラしていない）に「表示」「非表示」を書き出し、インポート時に読み戻せるようにした。
- エクスポート時の並び順を「非表示レシピが上・表示レシピが下」にグループ分けするよう変更（一括で表示/非表示を編集しやすいように）。
- エクスポートは今後、デフォルトで**表示・非表示すべてのレシピ**を対象にする（従来は表示レシピのみだった）。「表示レシピのみエクスポート」チェックボックスをエクスポート画面に追加したので、従来通りの挙動にしたい場合はこちらをON。
- **「全データをクリアして上書き」を本当の物理削除に変更**（`prisma.recipe.deleteMany`）。これにより、クリア後に非表示のゴミが残ることが無くなる。ただし後述8.3の理由で、物理削除に失敗した場合は自動的に従来の非表示化にフォールバックするようにしてある（無言で500エラーにはならない）。
- レシピ一覧の「非表示レシピ」画面に「非表示レシピを全て完全に削除」ボタンを追加（`DELETE /api/recipes/bulk-delete-hidden`という新しいAPIを新設）。非表示にしただけで満足せず完全に消したいユーザー向け。2段階の確認ダイアログあり、元に戻せない旨を明示。

### 8.3 ★★★ 必ず `npx prisma db push` を実行してください ★★★

`prisma/schema.prisma`の`Label`モデルの`recipe`リレーションに`onDelete: Cascade`を追加した（今まで指定が無く、ラベル発行履歴のあるレシピを物理削除しようとすると外部キー制約エラーになっていたため）。

**この`db push`を実行するまでは**：
- 「非表示レシピを全て完全に削除」ボタン
- 「全データをクリアして上書き」（クリア部分が物理削除に変わったため）

の2つは、ラベルを1回でも発行したことがあるレシピが対象に含まれると失敗する可能性がある（コード側で失敗時に安全な形にフォールバック/エラーメッセージ表示はしているので、アプリが落ちたりデータが壊れたりはしないが、機能としては使えない）。

デプロイ後、忘れずに`npx prisma db push`を実行してください（`prisma migrate dev`は今までどおり使わないこと）。これは4章に書いた`data_transfer_logs`テーブルのdb pushとは別件・追加の変更点です。**両方が反映されているか、一度まとめて確認することを推奨**。

### 8.4 動作確認してほしいこと

- 上記の「110件/98件/167件」を再現したアカウントで、`db push`後に改めて「全データをクリアして上書き」でインポートし直し、非表示レシピが積み上がらず、期待通りの件数になるか確認。
- 「非表示レシピを全て完全に削除」ボタンで実際に非表示レシピが消えるか確認。
- 非表示レシピと同名のレシピを（上書きONで）再インポートし、重複作成されず、かつ非表示状態が維持されるか確認。
