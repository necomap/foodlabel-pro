# FoodLabel Pro セキュリティ監査レポート（2026-09-27）

「第三者からの攻撃・改ざん・不正ログインを防ぎたい」というご依頼を受けて、認証・認可・入力値の扱い・依存パッケージ・HTTPヘッダーを中心に確認しました。見つかった問題はコードで直せるものはその場で修正し、PCへ書き戻し済みです。`npm install`の実行と、その後の動作確認をお願いします。

## 最重要（優先して対応してください）

### 1. Next.js自体に「認証を丸ごとすり抜けられる」既知の脆弱性があった
このアプリのログイン必須チェック・管理者判定（`middleware.ts`）は、使っているNext.js 14.2.5に存在する脆弱性（CVE-2025-29927）の影響を受ける対象でした。特定のHTTPヘッダーを付けてリクエストするだけで、この`middleware.ts`のチェック自体を丸ごと無視させることができる、というものです（世界的に知られている脆弱性で、修正版が出てから攻撃の試みが多数報告されています）。
実際には各API側でもログインチェックを個別に行っている箇所が多く、データが即座に盗まれる状態ではありませんでしたが、`/admin`画面の保護（Basic認証・管理者判定）がこの手口で丸ごと無効化されうる状態でした。
**対応**: `package.json`の`next`を`14.2.35`（14系で最後にセキュリティ修正が入ったバージョン）に更新済みです。`npm install`を実行してください。
なお、Next.js 14系自体が2025年10月末でサポート終了（EOL）しているため、今後新しく見つかる脆弱性には修正が提供されません。今回はひとまず14系の最終安定版に上げましたが、中長期的にはNext.js 16系への移行を計画することを推奨します（大掛かりな作業になるため、今回の対応には含めていません）。

### 2. ログインの総当たり攻撃（ブルートフォース）対策が実質機能していなかった
データベースには「ログイン失敗回数」「ロック期限」の項目が用意され、ロック中かどうかのチェックも実装されていましたが、**肝心の「失敗回数を実際にカウントアップする処理」がどこにも実装されていませんでした**。そのため、パスワードを何度間違えてもロックが一切かからず、他人のアカウントへの総当たりパスワード攻撃を制限なく試行できる状態でした。
**対応**: `lib/auth.ts`に、5回失敗したら15分間ロックする処理を追加しました。

### 3. レシピ印刷（保健所提出用一括印刷）にXSS（他人の入力がスクリプトとして実行されうる）の穴があった
レシピ名・材料名・作り方・備考などを印刷用HTMLに埋め込む処理（`app/dashboard/recipes/print/page.tsx`）が、これらの文字列を一切エスケープしていませんでした。通常は自分の入力なので実害が出にくいですが、**他ユーザーが登録して共有食材として承認された材料名にスクリプトを仕込まれた場合、それを使って印刷した別のユーザーの画面でスクリプトが実行されてしまう**、という第三者攻撃の経路になり得ました（印刷は同一オリジンのiframeで開くため、実行されると印刷した本人のログインセッションを使って裏で操作されるリスクがあります）。
**対応**: 該当箇所すべてにHTMLエスケープ処理を追加しました。ラベル生成（`lib/label.ts`）側は元々ほぼエスケープ済みでしたが、店舗ロゴ画像のURLだけエスケープ漏れがあったため、あわせて修正しました。

## 中程度（修正済み）

- **ロゴ画像アップロードの検証が甘かった**: アップロードされたファイルが本当に画像かどうかを、ブラウザが申告する情報（偽装可能）だけで判断していました。ファイルの中身（先頭バイト）を見て実際にPNG/JPEG/GIF/WEBPかを確認する処理に変更し、スクリプトを埋め込めるSVG形式は明示的に拒否するようにしました。
- **店舗のロゴURL・QRコードURLが未検証だった**: 画面上は必ずアップロード機能経由でしか設定されませんが、API（`/api/shops/[id]`）を直接叩けば任意の文字列を保存できてしまう作りだったため、http(s)から始まるURLのみを受け付けるよう多層防御を追加しました。
- **セキュリティ関連のHTTPヘッダーが一切設定されていなかった**: クリックジャッキング対策（X-Frame-Options）・MIMEスニッフィング対策（X-Content-Type-Options）等、影響の小さいものを追加しました。より強力なContent-Security-Policyは、印刷まわりでインラインstyle/scriptを多用しているため、動作確認なしに入れると印刷機能を壊すリスクがあり、今回は見送りました。
- **xlsxパッケージ（Excelインポート・エクスポート機能で使用）に既知の脆弱性**: 高危険度のReDoS（悪意あるファイルでサーバーを固まらせる）と中危険度のプロトタイプ汚染の脆弱性があり、npm公式レジストリでは未修正のままでした。修正版はSheetJS社自身の配布元からのみ入手できるため、`package.json`のインストール元をそちらに向くよう変更しました。

## 確認したが問題なし（現状のままで良い）

- 主要なAPI（レシピ・食材・店舗・ラベルテンプレート等）は、他人のデータを直接ID指定で操作できないよう、必ずログインユーザー自身のデータかを絞り込んでから処理しており、いわゆるIDOR（他人のデータへの不正アクセス）のリスクは見当たりませんでした。
- 管理者専用API（`/api/admin/*`）は、`middleware.ts`だけに頼らず、各APIが個別に「管理者プランかどうか」をサーバー側で再チェックしており、①の脆弱性が悪用された場合でも管理者データそのものが漏れる作りにはなっていませんでした。
- Stripe Webhookは署名検証を正しく実装済みです。
- Cron（バックアップ・keepalive）は`CRON_SECRET`によるBearer認証で保護されており、外部から自由に叩ける状態ではありません。
- 3アプリ連携用の外部APIキー（`/api/external/recipes`）は、以前あった「認証なしで全ユーザーのレシピが見える」不具合が既に修正済みで、192bitのランダムキーによる本人確認が正しく機能しています。
- パスワードはbcryptでコスト12でハッシュ化、パスワードリセット・メール認証トークンは32バイトのランダム値かつ有効期限・使い切り制限ありと、いずれも妥当な実装でした。

## 今回やり残したこと（整合性チェック・全般バグチェック）

ご依頼いただいた「全体の整合性チェック・バグチェック」は、セキュリティ以外の一般的な不具合（表示の崩れ、計算ミス、機能同士の食い違いなど）をアプリ全体で洗い出す、セキュリティとは別の大きな作業になります。今回はセキュリティ対応で分量が大きくなったため着手できていません。このセッションはかなり長くなっているため、続けて行う場合は新しいチャットに引き継ぐことをおすすめします（引き継ぎ文書を別途用意します）。

## お願いしたいこと

1. PCで`npm run db:push`は既に完了済みとのことなので、今回の分は**`npm install`**を実行してください（`next`・`xlsx`のバージョンを変更したため）。
2. GitHub Desktopでコミット→push（今回変更したファイル一式）。
3. デプロイ後、ロゴ画像のアップロード・レシピ印刷・ログインが問題なく動くか一度確認してください。
