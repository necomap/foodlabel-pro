## 2. 次のチャットで最初にやること：まとめてラベル印刷（ユーザー要望・最優先）

**背景**: 10種類などをまとめて印刷するとき、1レシピずつラベル印刷画面で期限・枚数を入れて印刷するのが非常に手間。

### 仕様（11/12 ユーザーと確定）
1. **入口**: レシピ一覧のチェックボックス（既存の `selected`、`app/dashboard/recipes/page.tsx`）で選び、新ボタン「○件のラベルをまとめて印刷」→ 新画面 `/dashboard/labels/batch?ids=...`
   - 既存の「○件を印刷」（レシピ表の印刷 `/dashboard/recipes/print`）とは別ボタン。混同しない文言にする
2. **まとめ画面**: 選んだレシピを1行ずつ表示。各行に **期限日（日付を直接入力）** と **枚数**
   - 期限日の初期値 = 製造日（画面上部で共通指定、初期値は今日）＋ 各レシピの賞味/消費期限日数。必要な行だけ書き換える
   - 行の削除・並べ替え（任意）、合計枚数の表示
3. **印刷設定は「ラベル印刷画面で最後に使った設定」をそのまま使う**（用紙・フォント・店舗・表示項目・言語など）。ラベル画面はブラウザに保存済み（`getL` / `updateLabelStorage`、localStorage）なので同じキーから読む。まとめ画面には「設定はラベル印刷画面で変更」と案内と現在の設定の要約を表示
4. **A4シール用紙は続けて詰める**（Aを3枚、Bを5枚…と空きなく。改ページはシートが埋まったときだけ）。開始位置（`startPosition`）は最初のレシピにだけ適用
   - ラベルプリンター（QL）の場合は順番に連続出力
   - b-PAC印刷にも対応（`lib/bpac-print.ts` の `printFoodLabel(template, content, copies)` を各レシピで順に呼ぶ。11/12に枚数指定対応済み）
5. **セット保存**: 「朝の焼き菓子セット」のように名前を付けて「レシピと枚数」を保存し、次回ワンクリックで呼び出す（期限日は呼び出し時に再計算）
   - 複数端末・複数人で使えるよう **DBに保存**: 新モデル例 `LabelPrintSet { id, userId, name, items Json /* [{recipeId, count}] */, createdAt, updatedAt }` → **ユーザーが `npm run db:push`**
   - 呼び出し時、削除・非表示になったレシピは除外して知らせる

### 実装メモ
- 現在の生成API `app/api/labels/generate/route.ts` は1レシピ単位（`manufactureDate`＋`shelfLifeDays` を受け取る。期限日指定は shelfLifeDays = 期限日 − 製造日 に変換すれば流用可）
- A4を続けて詰めるには、複数レシピのラベル内容をまとめて1つのHTMLに配置する必要がある → **新API `app/api/labels/generate-batch/route.ts`** を作り、各レシピについて既存と同じ内容生成（`generateLabelContent`）を行い、`generateLabelHtml`（`lib/label.ts`）を「[{content, count}] の配列を受け取って順に面付けする」形に拡張（または面付け部分を関数に切り出す）
- **既存のgenerateが行っている処理を必ず全部引き継ぐ**: プランの月間印刷枚数上限チェック（合計枚数で判定）、`label_print_logs` への記録（レシピごと）、ロット情報の記録、確認記録、英語ラベル分岐、警告の収集（レシピ名付きでまとめて表示）
- 共通化のため、generate route の「レシピ → recipeDetail → content」部分を関数に切り出してから両APIで使うのが安全
- 仕上げ: ヘルプ（`app/dashboard/help/page.tsx`）・ユーザーマニュアル・仕様書の修正履歴にも追記

## 3. その後にやること：無料で追加できる新機能（類似サービス調査より）

ユーザー方針: **AI利用料などの継続費用がかからない機能は一通り入れたい**。手書きレシピの読み取り（AI）は課金ユーザーが増えてから（`docs\機能アイデア_バックログ.md` に記録済み）。

**進め方の推奨**: Next.js 16 を main にマージしてから、新しいブランチ（例 `feature-reports`）で作業する。1機能ずつ「実装 → クラウドで tsc/build → PCへ書き戻し → プレビュー確認」。

### 優先順位と概要

| 順 | 機能 | 作業量 | DB変更 |
|---|---|---|---|
| 1 | アレルゲン一覧表 | 小 | なし |
| 2 | 栄養強調表示の判定 | 小〜中 | なし |
| 3 | 商品規格書のPDF出力 | 中 | なし（項目追加するなら有） |
| 4 | POP・プライスカード印刷 | 中 | 価格を保存するなら有 |
| 5 | 英語ラベル用の店名・住所 | 小 | **有**（ユーザーが `npm run db:push`） |

### 3-1. アレルゲン一覧表
- 全レシピ（表示中のもの）× 特定原材料等28品目の ○ 表。店頭掲示・問い合わせ対応用
- アレルゲンの集計は `lib/allergen.ts` の `collectRecipeAllergens`（10/28以降はマスタ紐づけ材料は**食材マスタのアレルゲンのみ**を使う。ラベルと同じ結果になるよう同じ関数を使うこと）
- 品目と並び順: `REQUIRED_ALLERGENS`（義務）→ `OPTIONAL_ALLERGENS`（推奨）。義務と推奨は列の色や見出しで区別
- 画面案: `app/dashboard/allergen-table/page.tsx` ＋ API `app/api/recipes/allergen-table/route.ts`。カテゴリ絞り込み、A4横向き印刷（`lib/print-html.ts` の `printHtmlDocument`、iframe方式）
- 注意書きを表の下に入れる（「本表は各商品の原材料に基づくもので、製造ラインでのコンタミネーションは含みません」等の文言はユーザーに確認）
- ナビ: `app/dashboard/_nav.tsx` に追加

### 3-2. 栄養強調表示の判定
- 「低カロリー」「糖類ゼロ」「たんぱく質たっぷり」など、食品表示基準の栄養強調表示の条件を満たすかを、レシピの栄養成分（100g または 100ml あたり）から判定して表示する
- **基準値は記憶で書かず、消費者庁の食品表示基準（別表第12・第13 など）を WebSearch/WebFetch で確認してから実装**すること
- 表示場所: レシピ詳細画面に「表示できる可能性のある強調表示」欄。あくまで目安で、実際に表示する場合の注意（比較対象の明記が必要な「〇〇%カット」等）を添える
- 100gあたりの計算には総重量（`contentAmount`・歩留まり `wasteRatio`）が必要。既存の栄養計算（`lib/nutrition.ts`、`computeLiveRecipeNutrition`）を使う

### 3-3. 商品規格書のPDF出力
- 卸先・道の駅・百貨店向け。1商品1ページ（A4縦）
- 項目案: 商品名／名称／原材料名（ラベルと同じ文字列）／アレルゲン（28品目の○×表）／栄養成分（1個あたり＋100gあたり）／内容量／賞味・消費期限／保存方法／製造者／配合表（材料・重量・配合率％。**配合は企業秘密の場合があるので出力ON/OFFを選べるように**）／作成日
- データはラベル生成と同じ組み立て（`app/api/labels/generate/route.ts` の recipeDetail 作成部分）を流用できるか確認。共通化できるなら関数に切り出す
- 出力は HTML → ブラウザ印刷で PDF 保存（新しい依存を増やさない）

### 3-4. POP・プライスカード印刷
- 店頭用カード（商品名・価格・アレルゲンアイコン・一言コメント）。サイズはカード（91×55mm）・A6・A4に複数面付け
- 価格はレシピに無ければ印刷時に入力（保存するなら Recipe に `price` 追加＝DB変更）
- アレルゲンアイコンは文字バッジで代用可（画像素材を増やさない）

### 3-5. 英語ラベル用の店名・住所
- `prisma/schema.prisma` の `Shop` に `shopNameEn`・`addressEn`（任意）を追加 → **ユーザーがPCで `npm run db:push`**（スキーマ変更の手順は 20261029 の文書参照）
- 店舗設定画面に入力欄、`lib/label.ts` の英語ラベル（`config.language === 'en'` の分岐）で未入力なら日本語のまま
